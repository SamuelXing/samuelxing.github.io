A working tour of io_uring: why every prior Linux async I/O option was a compromise, why "just add more threads" stops scaling, how the two-ring design works, what the Rust ecosystem looks like, and who actually runs it in production (and who has turned it off).

## The setup: Linux had three async stories, and all three were bad

Before io_uring landed in **Linux 5.1 (May 2019)**, you had three ways to do I/O on Linux. Each one was a compromise.

**1. Synchronous syscalls plus a thread pool.** `pread` and `pwrite` block on page-cache misses. The only way to get N reads in flight is N threads parked in `pread`. This is what glibc POSIX AIO does internally. It's also what MySQL, PostgreSQL, SQLite, and every other "we want concurrent buffered I/O" project ends up reinventing. The cost is real threads, real stacks, real context switches.

**2. `select` / `poll` / `epoll`.** These are *readiness* interfaces. They tell you when a file descriptor will not block — then you still do the read yourself. That works for things with a meaningful "ready" state: sockets, pipes, ttys, eventfds. For regular files it's meaningless: the fd is always "ready," and the actual `read()` still blocks on the page cache or the block layer. This is the single biggest reason nginx lives happily on epoll and Postgres doesn't.

**3. Linux AIO (`io_submit`/`io_getevents`).** Supposed to be the answer for files. Shipped with constraints that made it nearly unusable:

- True async only with `O_DIRECT`. On buffered files it silently falls back to blocking.
- Even with `O_DIRECT`, `io_submit` can still block on metadata, inode locks, or request-queue allocation.
- Two syscalls per batch, with marshalling.
- No fsync. No networking. No poll. Cancellation is best-effort.

Linus's reaction in the 2019 `aio_poll` LKML thread is the political context for io_uring: a *replacement*, not a patch, was acceptable upstream.

**The plain-English summary.** epoll only worked for sockets. libaio only worked for `O_DIRECT`. Everything else parked a thread.

## Why "just use threads" hits a wall

The third option above — parking a thread per in-flight I/O — is the only thing that always works for buffered files. So why isn't this fine? Because threads have hard ceilings, and you hit them sooner than you'd guess.

### The ceilings, in the order you hit them

| Ceiling | The number | Why it bites |
|---|---|---|
| **Default pthread stack** | 8 MB | 10K threads = 80 GB of virtual address space; even at 64 KB stacks, 100K threads = 6.4 GB just for stacks |
| **Context-switch cost** | ~1–3 μs direct, much more indirect | At 100K threads waking once per ms on 16 cores, you're scheduling ~100M switches/s — more CPU than you have |
| **`RLIMIT_NPROC`** | 4K–128K (per user) | The first soft cap you hit on a default distro |
| **`/proc/sys/kernel/threads-max`** | tens of thousands to a few hundred thousand | Memory-derived system-wide cap |
| **L2/L3 cache** | per-core, MB-scale | Every runnable thread evicts cache lines from threads that *are* doing work |

The direct context-switch number understates the problem. Eli Bendersky's microbenchmark puts pinned same-process switches at ~1.2–1.5 μs, but the *indirect* cost — L1/L2/TLB thrash, branch-predictor reset — is much larger and never shows up in the timer. Tsuna's numbers on an Intel E5-2620 land around 3,000 ns including the futex syscall.

### The historical name for this is C10K

Dan Kegel framed it in 1999: *"It's time for web servers to handle ten thousand clients simultaneously, don't you think?"* His point wasn't that the hardware was inadequate — a 1 GHz / 2 GB box of the era *could*, on paper, serve 20,000 clients. The bottleneck was the OS interface. The kernel's answer was a 20-year arc: `epoll` (2002) for socket readiness, `libaio` for `O_DIRECT` files, and eventually `io_uring` for everything.

Robert Graham's C10M talk (Shmoocon 2013) pushed the goal two orders of magnitude further and made the punchline blunt: *"the kernel is the problem, not the solution."* You reach C10M by removing threads from the I/O path — via DPDK, kernel bypass, or batched async APIs like io_uring.

### What this looks like in benchmarks

- **Apache vs nginx.** Apache prefork collapses around 1K–10K concurrent connections; nginx holds 100K+ on the same hardware. Memory cost: ~10 MB per connection for Apache prefork vs ~2.5 MB per *ten thousand* connections for nginx.
- **MySQL InnoDB I/O threads.** Official tuning guidance: only raise `innodb_read_io_threads` past 4 if you actually see ">64 × threads pending requests." Hard cap is 64, and the curve flattens long before. More threads do not buy more IOPS once you've saturated the queues.
- **PostgreSQL backends.** Each idle connection is 5–10 MB of private RAM plus context-switch tax. Citus's "Limits of Connection Scalability" piece shows throughput dropping sharply past a few hundred connections even when most are idle. This is why everyone runs PgBouncer.
- **WhatsApp on Erlang/BEAM.** Famously hit 2M concurrent TCP connections per FreeBSD server — only possible because BEAM processes are kilobytes and scheduled in userspace. Same shape as Go goroutines and Java virtual threads (JDK 21): make the scheduling unit small enough that "one per request" is no longer crazy.

**The pattern.** Every "we scaled to a million" story is the same story: stop using kernel threads as your unit of concurrency.

### The mnemonic

> **Thread-per-IO ties peak concurrency to peak thread count.** Threads are scheduler entities. Scheduler entities are expensive. You bottom out around 10K–100K, often much sooner due to RAM or context-switch overhead.

io_uring breaks this because peak concurrency becomes *peak submission-queue depth* — which is a memory allocation, not a scheduler entity. One ring can hold 32,768 in-flight ops (`IORING_MAX_ENTRIES`) for the cost of a couple hundred KB of mmap'd memory. One ring per core gives you millions. The kernel does the work in batched async paths; nothing is parked.

That's the whole pitch in one sentence: **io_uring decouples concurrency from threads.**

## How it actually works: two rings, shared memory

The kernel exposes exactly three syscalls:

| Syscall | Purpose |
|---|---|
| `io_uring_setup(entries, params)` | Create the instance, return an fd |
| `io_uring_enter(fd, to_submit, min_complete, flags, sig)` | Submit, wait, or both |
| `io_uring_register(fd, opcode, arg, nr)` | Pre-register long-lived resources (buffers, files, eventfds) |

`io_uring_setup` mmaps **two ring buffers** into your process:

- **SQ — submission queue.** Userspace produces, kernel consumes. 64-byte SQEs.
- **CQ — completion queue.** Kernel produces, userspace consumes. 16-byte CQEs, each tagged with a `user_data` cookie you choose.

```
┌─────────── userspace ───────────┐     ┌─────────── kernel ──────────┐
│                                  │     │                              │
│  write SQE  ──►  SQ ring ──────────────►  pick up SQE, do the IO     │
│                  (mmap)          │     │                              │
│                                  │     │                              │
│  read CQE  ◄──   CQ ring  ◄────────────  post CQE on completion      │
│                  (mmap)          │     │                              │
└──────────────────────────────────┘     └──────────────────────────────┘
                  ▲                                   ▲
                  └─────── shared memory, no copy ────┘
```

Head and tail indices live in shared memory with release/acquire ordering. **Enqueueing an SQE is a memory write. Dequeueing a CQE is a memory read.** No syscall is needed for either. The only thing the syscall does is *kick* the kernel to come look at the queue.

This is the whole reason libaio's problems disappear:

- **No per-submission copy.** The SQE is already in kernel-visible memory.
- **Batching is free.** Write N SQEs, do one `io_uring_enter`.
- **The opcode is an open enum.** New ops (`IORING_OP_*`) extend the ABI without a new syscall.

### The advanced knobs (and what each one buys you)

| Knob | What it does | When you want it |
|---|---|---|
| **`SQPOLL`** | Kernel thread polls the SQ tail | Steady-state datapath where you submit constantly — eliminates `io_uring_enter` entirely |
| **`IOPOLL`** | Kernel busy-polls NVMe completions instead of taking the irq path | `O_DIRECT` on polled-capable NVMe; trades CPU for tail latency |
| **Registered buffers** | Pin user pages once via `IORING_REGISTER_BUFFERS` | Long-lived buffer pool; skips `get_user_pages`/`put_user_pages` per op |
| **Registered files** | Index into a kernel-side table instead of fd lookup | Hot fds in long-running servers; skips `fget`/`fput` per op |
| **Linked SQEs** | `IOSQE_IO_LINK` chains ops — second runs only if first succeeds | WAL patterns: `write(data) → write(commit) → fsync` without a userspace round-trip |
| **Multishot** | One SQE produces many CQEs (`accept`, `recv`, `poll`) | Accept loops, RX queues — submit once, harvest forever |

**Mnemonic.** SQPOLL kills the syscall. IOPOLL kills the irq. Registered buffers/files kill per-op setup. Linked SQEs kill round-trips. Multishot kills resubmission.

### Evolution at a glance

| Kernel | Year | What landed |
|---|---|---|
| **5.1** | 2019 | Initial merge: read/write/fsync/poll, SQPOLL, IOPOLL, registered buffers/files |
| **5.5–5.6** | 2020 | Networking: `send`, `recv`, `accept`, `connect` |
| **5.7** | 2020 | Async buffered reads — file I/O finally async without `O_DIRECT` |
| **5.13** | 2021 | Provided/selected buffers — kernel picks a buffer at completion |
| **5.19–6.0** | 2022 | Multishot ops; zero-copy send (`IORING_OP_SEND_ZC`) |
| **6.x** | 2022+ | NAPI busy-polling, ring messages, registered ring fds, futex ops; opcode count now 60+ |

## The Rust ecosystem

Nobody calls the raw syscalls directly. The C reference wrapper is **liburing** (Axboe's official library, currently 2.14). Rust has its own stack on top.

| Crate | Model | Best for |
|---|---|---|
| `io-uring` (tokio-rs) | Low-level, `unsafe`, 1:1 with liburing | Building runtimes; custom event loops |
| `tokio-uring` | Async runtime on `io-uring` with owned-buffer API | Tokio users who want io_uring on Linux; still pre-1.0 |
| `glommio` (DataDog) | Thread-per-core, shared-nothing, io_uring-native | Storage engines, latency-sensitive shards |
| `monoio` (ByteDance) | Thread-per-core, has an epoll fallback | Proxies/gateways at ByteDance scale |
| `compio` | Completion-based, cross-platform (io_uring / IOCP / kqueue) | Single API across Linux/Windows/macOS |

### Why mainline Tokio doesn't use io_uring

This trips a lot of people up.

- **Tokio's reactor is readiness-based.** epoll says "fd is now readable, *you* do the syscall." The buffer is owned by the caller, valid for one poll, free to drop right after.
- **io_uring is completion-based.** *You* hand the kernel a buffer, *the kernel* fills it later. The kernel needs that buffer pointer stable for the entire op.

That collides with Rust's `AsyncRead`/`AsyncWrite` traits, which take a `&mut [u8]` that's only valid for the current poll. You can't safely give a borrowed slice to the kernel — the future might be dropped, the slice might go away, the kernel still writes into it. `tokio-uring` solves this by introducing *owned-buffer* traits: `read_at(buf) -> (Result<usize>, Buf)`. The buffer is moved into the kernel and returned in the result tuple. That works, but it's a different API.

Cancellation makes it worse. You can't synchronously cancel an in-flight kernel op without leaking the buffer (the kernel might still be writing to it when you try to free it). Every io_uring runtime in Rust handles this with some flavor of "buffer ownership lives with the operation, not the future."

**The mnemonic.** Readiness API → borrowed buffers. Completion API → owned buffers. Tokio chose readiness; io_uring is completion. The mismatch is structural, not a missing feature.

## A small Rust example: low-level

`Cargo.toml`:

```toml
[dependencies]
io-uring = "0.7"
```

`src/main.rs`:

```rust
use io_uring::{opcode, types, IoUring};
use std::os::unix::io::AsRawFd;
use std::{fs::File, io};

fn main() -> io::Result<()> {
    // 1. Set up a ring with 8 SQ/CQ entries.
    let mut ring = IoUring::new(8)?;

    // 2. Open the file synchronously (could also use opcode::OpenAt).
    let file = File::open("/etc/hostname")?;
    let fd = types::Fd(file.as_raw_fd());

    // 3. Buffer MUST outlive the in-flight op. The kernel will write to it
    //    later — drop it early and the kernel writes into freed memory.
    let mut buf = vec![0u8; 1024];

    // 4. Build a Read SQE. user_data is an opaque u64 we get back in the CQE.
    let read_e = opcode::Read::new(fd, buf.as_mut_ptr(), buf.len() as _)
        .offset(0)
        .build()
        .user_data(0x42);

    // 5. Push onto the submission queue. The `unsafe` is the API forcing you
    //    to acknowledge the buffer-lifetime invariant.
    unsafe {
        ring.submission()
            .push(&read_e)
            .expect("submission queue full");
    }

    // 6. Submit and block until at least one completion is available.
    ring.submit_and_wait(1)?;

    // 7. Reap the CQE.
    let cqe = ring.completion().next().expect("no completion");
    assert_eq!(cqe.user_data(), 0x42);
    let res = cqe.result();
    if res < 0 {
        return Err(io::Error::from_raw_os_error(-res));
    }
    let n = res as usize;

    println!("read {n} bytes: {}", String::from_utf8_lossy(&buf[..n]));
    Ok(())
}
```

The shape is always the same: build an SQE, push it onto the SQ, kick the kernel, harvest CQEs. The `unsafe` block exists because the SQE stores a raw pointer into your buffer and the kernel won't touch the borrow checker.

## The same thing, high-level

`Cargo.toml`:

```toml
[dependencies]
tokio-uring = "0.5"
```

```rust
use tokio_uring::fs::File;

fn main() {
    tokio_uring::start(async {
        let file = File::open("/etc/hostname").await.unwrap();
        let buf = vec![0u8; 1024];
        // Owned-buffer API: `buf` moves in, comes back out in the result.
        let (res, buf) = file.read_at(buf, 0).await;
        let n = res.unwrap();
        println!("read {n} bytes: {}", String::from_utf8_lossy(&buf[..n]));
        file.close().await.unwrap();
    });
}
```

No `unsafe`, no manual SQE bookkeeping. The price is the owned-buffer signature: `read_at` *consumes* your buffer and hands it back. That's the visible shape of "completion-based, but safe."

## What the benchmarks actually say

### Storage

The canonical numbers come from [Axboe's paper](https://kernel.dk/io_uring.pdf), 4K random reads against Optane:

| Mode | IOPS | Syscalls/op |
|---|---|---|
| Synchronous `read()` | ~1.7M | 1 |
| libaio | ~1.8M | ~2 |
| io_uring, interrupt-driven | ~1.7M | ~0 (coalesced) |
| io_uring + IOPOLL | ~1.97M | ~0 |
| **io_uring + SQPOLL + IOPOLL** | **~2.7M** | **0** |

A second widely-quoted result from the same paper: at QD128 on a single Optane SSD, libaio peaks around 608K IOPS while io_uring with registered files+buffers hits 1.62M IOPS — a 2.6x edge, almost entirely from syscall and per-op setup elimination.

Phoronix retests across 5.6 and 6.x kernels are consistent: the bigger your queue depth and the smaller your block size, the more io_uring wins. At QD=1 or large sequential I/O, the three APIs converge to within a few percent.

**Plain-English rule.** io_uring's storage win is "I eliminated the per-op syscall cost." If your workload doesn't generate enough in-flight ops for that cost to matter, you won't see the win.

### Networking

The story flips. Cloudflare's [*Missing Manuals — io_uring worker pool*](https://blog.cloudflare.com/missing-manuals-io_uring-worker-pool/) found their proxy workloads got *slower* with a naive io_uring port. Socket ops kept taking the async-offload path (`io-wq`) and incurring extra wakeups. They had to use `IORING_OP_PROVIDE_BUFFERS` + multishot `recv` + careful `IOSQE_ASYNC` tuning to claw back parity with epoll.

Zero-copy send (5.19+) gives ~20–30% TX throughput improvement over `sendmsg` by skipping the user-page copy. RX gains are smaller, ~5–15%, and only at large batches.

**Plain-English rule.** For typical L7 proxies (lots of short connections, modest QD), epoll is still competitive or better. io_uring wins decisively only when you can keep many ops in flight and use the zero-copy / multishot paths.

## Who actually uses it

**Single-tenant systems where the operator controls the kernel:**

- **ScyllaDB / Seastar** — Seastar's reactor used libaio from the start; ScyllaDB added an io_uring backend for lower latency variance in their thread-per-core model.
- **Glommio (DataDog)** — io_uring-first runtime for high-throughput telemetry.
- **RocksDB** — `MultiRead` has an io_uring path that batches SST reads; Meta has reported double-digit tail-latency improvements.
- **PostgreSQL 18** (2025) — Andres Freund's AIO work landed with `io_method=io_uring`. pgconf.dev talks show 2–3x speedups on prefetch-bound sequential scans.
- **TigerBeetle, Redpanda** — io_uring-native.
- **QEMU** — `aio=io_uring` block backend, default on newer distros for virtio-blk.
- **fio** — `ioengine=io_uring` is the de facto reference for storage benchmarking.

**Where it's been turned off:**

In June 2023 Google disclosed that ~60% of kCTF-submitted kernel exploits in 2022–2023 used io_uring. Their response:

- Disabled on Google production servers (GCE/Borg).
- Disabled in Android via seccomp filter.
- Disabled in ChromeOS.

The reasoning: shared SQ/CQ memory + 60+ opcodes (each its own state machine) + async-worker reference counting produced a steady stream of UAF and type-confusion bugs. User-controlled memory drives kernel state machines, which is a fundamentally larger attack surface than `read`/`write`/`epoll`. Kernel 6.6 added a `kernel.io_uring_disabled` sysctl so distros can gate it.

**The split is clean.** Single-tenant, trusted, performance-sensitive: io_uring. Multi-tenant, untrusted, defense-in-depth: turn it off.

## When to reach for io_uring (decision framework)

```
What are you building?
├─ L7 proxy with lots of short TCP connections
│    → epoll is still fine; io_uring needs careful tuning to even match it
│
├─ Storage engine / database / write-ahead log
│    → io_uring is the answer. Buffered + O_DIRECT in one API,
│      linked SQEs for WAL chains, registered buffers for the buffer pool.
│
├─ Thread-per-core executor (Seastar/Glommio/Monoio shape)
│    → io_uring is the natural fit. Submit and reap on the local ring,
│      no cross-core IPI for completion.
│
├─ General-purpose async runtime (Tokio shape)
│    → Use epoll. The completion/readiness mismatch is real;
│      tokio-uring is opt-in for the Linux path that needs it.
│
└─ Multi-tenant host running untrusted code
     → Turn it off. The CVE history is not theoretical.
```

### What you actually have to know

1. **The ring is the unit of concurrency** — not the thread. Size the SQ to the in-flight depth you want.
2. **Buffers live with the operation**, not the future. This is true at every layer, raw or wrapped.
3. **SQPOLL is the biggest single lever.** Then IOPOLL on polled NVMe. Then registered buffers/files.
4. **Linked SQEs** are how you build atomic multi-op patterns without a userspace round-trip.
5. **Always have an epoll fallback.** Distros and container runtimes increasingly disable io_uring by default.

## Misconceptions worth retiring

**"io_uring is just async I/O."** It's not. epoll is async (for readiness). io_uring is async *and* eliminates the per-op syscall *and* eliminates the buffer copy *and* works on any fd type. Each of those is a separate, additive win.

**"More threads = more I/O parallelism."** Only up to ~10K–100K, and with severe diminishing returns long before. Threads are scheduler entities. io_uring's SQEs are not.

**"io_uring is faster for everything."** For storage at high QD, yes. For typical L7 proxies, often no — epoll is hard to beat for short-lived sockets with low per-connection QD.

**"You should use the raw `io-uring` crate."** Almost never. Use `tokio-uring`, `glommio`, `monoio`, or `compio` unless you're building a runtime yourself.

**"io_uring replaces epoll."** It supplements epoll. epoll still ships in every kernel and works fine for socket-only workloads. io_uring's killer use case is the workloads epoll could never serve — buffered files, mixed file+socket, high-QD storage.

**"Completion-based and readiness-based are interchangeable."** They're not, and Rust makes the difference visible: readiness lets you borrow buffers, completion forces you to own them. That single fact is why `tokio` and `tokio-uring` have different APIs.

## The one-line distillations

> **The problem.** Pre-io_uring, you could pick async-for-sockets (epoll), async-for-O_DIRECT (libaio), or "park a thread" (everything else). Threads bottom out around 10K–100K. The other two left huge gaps.
>
> **The mechanism.** Two mmap'd ring buffers between userspace and kernel. Enqueueing an SQE is a memory write. Dequeueing a CQE is a memory read. No syscall required for either, only for the kick.
>
> **The scaling win.** Concurrency is no longer tied to thread count. It's tied to SQ depth, which is a memory allocation. One ring per core gets you millions of in-flight ops without parking anything.
>
> **The constants.** ~2.7M IOPS vs ~1.7M sync on Optane. ~2.6x over libaio at QD128. Negligible win at QD=1. Often a wash or worse for short-connection TCP proxies until you tune carefully.
>
> **The caveat.** Big attack surface. Turned off by default in Android, ChromeOS, and Google production. The right home is single-tenant trusted infrastructure — exactly where database and storage engines live.

The short version: **io_uring is the first Linux I/O interface that is general, truly async, and cheap — all three at once.** If your performance ceiling has historically been "Linux AIO is broken so we run a thread pool," it's the first credible exit.
